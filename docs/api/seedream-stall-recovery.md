# Seedream 提交不确定导致综合任务卡住（2026-11-19）

## 线上证据

客户在北京时间11:09反馈“会卡任务”。当时两个综合任务（单张与批量子任务）均处于processing：

- `task_extract_pattern_0e3772a2280b`
- `task_extract_pattern_10d8b46291b0`

每个任务的Gemini Pro、GPT、RunningHub三路结果都已持久化；Seedream只有 `state=submission_unknown`，没有taskid。
旧版将这个状态当作可恢复的生成等待，整体交给watchdog每12分钟重试，直到两次重试后失败退款；已生成的三张图因此没有交付。

这确认了应用的异常处理缺口，但原记录没有保存底层异常类型，**不能据此确定这两单最初一定是并发不足**。

另已离线复现：限流器在执行HTTP回调之前抛出Acquire Timeout（没有发出任何请求），旧代码也会记录submission_unknown。
修复不增加并发上限，不调整共享Redis限流池，也不修改原有积分规则。

## 状态与结算修复

| 状态 | 是否可能已经发送POST | 处理 |
| --- | --- | --- |
| waiting_for_slot | 否 | 未提交；名额等待失败正常报错，不进入“提交未知”的watchdog等待；恢复可安全尝试 |
| submitting / submission_unknown，无taskid | 是 | 禁止自动重发；终结无效等待。综合交付其他可用结果，独立任务失败按原规则退款 |
| submitted，有taskid | 是且已确认 | 只查询同一任务，不重新POST |
| completed / savedResults | 是且已有结果 | 重试下载或直接复用缓存，不重新生图 |

提交前的持久化回调放到限流器真正获得名额之后、HTTP请求执行之前。
失败记录仅加入exceptionType/httpStatus，不把密钥、参考图、指令或完整响应写入诊断字段。

综合分支等待预算结束时，如果其他分支有图片，直接交付；如果没有图片且Seedream有可查询任务号，保留原异常的taskid/诊断供watchdog恢复。
旧版已持久化的submission_unknown/submitting继续按“可能发送过”处理，不能凭新逻辑把它们改为可安全重发。

## 验证

126项相关后端测试通过，含：

- 没拿到并发名额 / Redis连接错误时HTTP请求数为0。
- 恢复“等待名额”后只产生一次POST。
- 等名额时取消，不误记为已提交；POST期间取消则保持防重复提交保护。
- POST超时、5xx、无效JSON、无效任务号均不会自动再次POST。
- 旧版不确定状态搭配三张缓存，可直接交付且所有上游HTTP调用数为0。
- 没有其他结果时，区分“有任务号的等待”和“无任务号的不确定提交”。
- 独立任务的等待保留积分，无法查询的不确定提交按原失败规则退款。

不新增付费生图测试。线上验证应优先复用已有缓存，检查任务状态、批量状态、实际下载及积分账目。
已失败并退款的旧任务不得自动重新扣费或重新生图；若人工恢复旧结果，需要单独记录并保留退款与交易凭证。
