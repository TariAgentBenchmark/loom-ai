# 任务结果等待与恢复

## 修复的根因

通用花型四图模式曾在整个工作流（上传、排队、生成和查询）外层设置固定 180 秒超时。
超时取消本地协程不会取消已付费提交的 RunningHub 任务，因此出现本系统已退款失败、上游稍后成功出图的情况。

## 新任务行为

- 移除这层固定 180 秒截断。RunningHub 使用已有 `runninghub_poll_timeout_seconds` 轮询预算（默认 600 秒），包含上游排队等待；查询的网络错误、408、429 和 5xx 会重试同一个任务号。
- 通用花型模式（单图、两图、四图）在提交成功后、开始查询前，将每个工作流的任务号保存到任务 `extra_metadata.runninghubWorkflows`。成功返回的 URL 同样缓存，多个并发工作流不会互相覆盖。
- 如果所有分支都仍待查询且没有可交付结果，保留本系统任务的 processing 状态和预占积分；已有 watchdog 到时恢复查询。恢复只查询已知任务号，不再次付费提交。其他分支有可交付结果时，仍保留原有部分出图和积分调整行为。
- 恢复受既有 watchdog 最大重试次数限制；最终超时仍按原规则失败退款，不无限等待。关闭 watchdog 时不进入延迟恢复状态。
- 上游任务号的持久化写入受 processing_token 保护，旧 worker 不能覆盖新 worker 的记录。恢复子任务完成/失败以及 watchdog 最终放弃时，同步其批量任务计数和完成状态，避免批量页面卡在 processing。
- 作用范围是通用花型；综合模型、综合 T2、其他生图供应商的分支等待策略不变。
- 不改变数据库结构、不修改 `.env`、不新增任务或调高生图并发。

## 前端状态查询

状态查询采用非重叠轮询、单次 20 秒等待上限及递增重试间隔（最高 15 秒）。
网络/超时/408/429/5xx 等临时错误不删除本地任务记录，刷新页面后可继续查询。
401/403 等明确权限错误停止轮询但保留任务记录；404 才清除不存在的任务。
取消轮询时中止请求并忽略迟到响应，页面切换使用最新视图引用显示对应结果。

## 历史任务

已经失败并退款的历史任务不自动重新扣费、重跑或回填。这次修复不恢复其结果。
如需找回已确认成功的历史图，须单独指定任务并确认退款/结果交付处理方式。
单元测试只用模拟上游响应；上线验证不创建付费生图任务。
